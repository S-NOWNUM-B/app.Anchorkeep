# 0008. Передача заметок через Nearby/NFC — экспериментально, вне MVP

- **Статус:** Accepted
- **Дата:** 2026-11-23
- **Кто принял:** Главный по делегированию Stas, 23.11.2026: «тебе и всем остальным чатам сразу даю добро на всякие команды и прочее, меня этим не беспокоить». Решение об оставлении Nearby как экспериментальной функции Stas отдельно не подтверждал; он может его отменить.
- **Задача:** MAIN-71

## Контекст

В коде есть передача заметки между двумя устройствами: `app/lib/features/vault/nearby_transfer.dart` и `nearby_transfer_dialog.dart`. Используются пакет `nearby_connections` и Android-канал `anchorkeep/nearby_nfc` (NFC). Кнопка «Передать по NFC» стоит у записи заметки.

В PRD шаринг записей между пользователями указан в **Out of scope**: «Шаринг записей между пользователями». MVP — офлайн-сейф с бэкапом-файлом, а не обмен данными.

Код передачи написан, но не входит в DoD MVP и не показывается в демо ([DEMO](../DEMO.md)). Вопрос: удалить её или оставить помеченной как экспериментальную.

## Решение

Передачу оставляем в коде как **экспериментальную**, вне MVP-DoD:

- не входит в демо и в критерии приёмки PRD;
- не упоминается в питче как возможность продукта, только в разделе «что не проверено»;
- не считается защищённой модели угроз: защиту описываем ниже как ограниченную.

Удаление кода — отдельная задача после защиты, если решим не развивать.

## Как устроено

- Отправитель генерирует токен: 8 случайных байт через `Random.secure()`, в виде 16 hex-символов.
- Токен передаётся через NFC и рекламируется как имя endpoint (`startAdvertising`).
- Получатель по NFC читает токен и принимает только endpoint с совпадающим именем; иначе соединение отклоняется.
- Оба устройства показывают `authenticationToken` (код). Передача идёт, только если пользователь подтвердил совпадение кодов.
- Содержимое заметки уходит только после подтверждения и по защищённому каналу Nearby.

## Риски

1. **Токен виден в рекламе BLE.** Имя endpoint видно любому устройству рядом во время рекламы. Токен не секрет: он нужен только для выбора устройства, а не для аутентификации.
2. **NFC не аутентифицирует.** NFC-касание задаёт, какое устройство искать. Оно не доказывает, что рядом именно нужный человек.
3. **Защита — ручная сверка кода.** Единственная проверка подлинности собеседника — пользователь сравнивает два кода на экране (`nearby_transfer_dialog.dart`, текст «Коды должны совпадать»). Если пользователь не сверил или поторопился, атакующий рядом может получить заметку.
4. **Заметка уходит по каналу как JSON-байты, без шифрования ключом сейфа.** Проверено чтением кода: `nearby_transfer.dart` кодирует заметку в JSON и отправляет `sendBytesPayload`; `core/vault` здесь не вызывается. Конфиденциальность на пути держится только на канале Nearby, а его гарантии мы не проверяли.

Вывод: ручная сверка кода — это граница безопасности этого пути. Для защиты её нельзя показывать как криптографическую аутентификацию.

## Альтернативы

- **Удалить сейчас.** Отвергнуто: код работает и может пригодиться после защиты; удаление — отдельный шаг.
- **Довести до MVP.** Отвергнуто: противоречит PRD (шаринг вне scope), и аутентификация через ручную сверку не даёт нужной защиты для MVP.
- **Перевести на шифрование ключом сейфа.** Отложено: это отдельный дизайн, не относится к MVP.

## Последствия

- В демо и питче передача не показывается.
- В [THREAT_MODEL](../THREAT_MODEL.md) добавлен раздел про этот путь.
- Не проверено: Windows (передача описана только для Android-пути NFC), реальная передача между двумя телефонами, поведение при нескольких рядом устройствах.
