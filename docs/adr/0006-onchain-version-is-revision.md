# 0006. On-chain `version` = `revision` заверенного файла

- **Статус:** Proposed
- **Дата:** 2026-10-21
- **Задача:** AK-14, AK-43

## Контекст

В исходном контракте `vault_registry` поле `VaultRecord.version` — счётчик заверений: `initialize_vault` ставит 1, каждый `commit_version` делает `+1`. А проверка бэкапа (F9) сравнивает `revision < onchain.version`, где `revision` из заголовка `.akv` растёт при **каждом сохранении**.

Это разные счётчики. Пример: сохранили сейф 42 раза, заверили 3 раза → `revision = 42`, `version = 3`. Старый бэкап с `revision = 30` даёт `30 < 3` → ложь → статус **Unknown** вместо **Outdated**. Демо-сценарий PRD «подсунули старый бэкап → Outdated» не работает.

## Решение

On-chain `version` хранит `revision` того файла, чей хеш заверен.

- `initialize_vault(vault_id, hash, version)` — `version` = `revision` файла.
- `commit_version(new_hash, new_version)` — `require!(new_version > record.version)`, иначе `VersionMismatch`; затем `version = new_version`.

Логика проверки F9 остаётся как в ARCHITECTURE.md и теперь сравнивает однородные величины.

## Альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Считать Outdated по `lastAnchoredRevision` из payload | Он лежит в текущем сейфе, а не в проверяемом бэкапе; на другом устройстве его нет |
| Хранить on-chain и счётчик заверений, и `revision` | Лишнее поле: счётчик заверений проверке не нужен |
| Оставить `expected_version == record.version` | Защищает от гонок, но не даёт сравнить бэкап с цепочкой |

## Последствия

- Монотонность `new_version > version` по-прежнему защищает от гонок двух устройств и не даёт заверить более старый файл поверх нового.
- `revision` защищён тегом AES-GCM (ADR 0005): поднять его в старом файле без пароля нельзя — расшифровка упадёт.
- В блокчейн уходит то же, что и раньше: pubkey, `vault_id`, число, SHA-256 (правило безопасности 7).
- Видно, сколько раз сохранялся сейф между заверениями — метаданные активности, уже упомянуты в PRD.
