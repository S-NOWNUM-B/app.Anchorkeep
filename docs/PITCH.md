# Питч-дек для защиты (MAIN-62)

Структура из 10 слайдов: проблема → решение → архитектура → демо → компромиссы и безопасность → roadmap. На каждом слайде: заголовок, 3–4 тезиса и что показываем на экране.

Факты берём из [PRD](PRD.md), [ARCHITECTURE](ARCHITECTURE.md), [THREAT_MODEL](THREAT_MODEL.md) и [REGRESSION_CORE](REGRESSION_CORE.md). Сценарий демо — [DEMO](DEMO.md).

---

## 1. Проблема

- Облачные менеджеры паролей требуют доверять чужому серверу.
- Локальные файлы-бэкапы легко подменить или откатить на старую копию.
- Шифрование защищает от порчи, но не от отката к старому валидному бэкапу.

**На экране:** один бэкап-файл и две его версии рядом, без подписи «какая актуальна».

## 2. Решение

- Локальный зашифрованный сейф без регистрации и сервера.
- При заверении в Solana devnet записываются публичный ключ, `vault_id`, версия и SHA-256 файла.
- При проверке приложение говорит: актуальная версия, устаревшая или неизвестная.

**На экране:** схема «файл → SHA-256 → запись в Solana»; внизу строка «секреты в блокчейн не попадают».

## 3. Архитектура

- Криптосхема: мастер-пароль → Argon2id → KEK → обёртка случайного ключа сейфа (VK) → AES-256-GCM.
- Заголовок файла входит в AAD: подмена заголовка ломает расшифровку.
- Solana: программа `vault_registry`, аккаунт `VaultRecord` (PDA), инструкции `initialize_vault` и `commit_version`; версия только растёт.
- Flutter, Android + Windows, один код.

**На экране:** упрощённая схема из ARCHITECTURE: три слоя `core/crypto`, `core/vault`, `core/solana`.

## 4. Демо: телефон → ПК → Verified

- Экспорт `.akbackup` на телефоне, восстановление на ПК.
- Проверка бэкапа: «Файл подтверждён».
- Заверение версии транзакцией в devnet.

**На экране:** живой прогон по [DEMO](DEMO.md), шаги 1–8.

## 5. Демо: старый бэкап → Outdated

- Подсунутый старый файл даёт «Бэкап устарел», а не «подтверждён».
- Это закрывает угрозу отката, которую не закрывает само шифрование.

**На экране:** шаги 9–10 из [DEMO](DEMO.md).

## 6. Компромиссы

- Потеря мастер-пароля = потеря данных. Это осознанно: восстановления нет by design.
- В блокчейне видно, когда и сколько раз заверяли, и что один владелец заверяет один сейф.
- Нужен интернет и devnet-SOL только для заверения и проверки; всё остальное офлайн.

**На экране:** три строки компромиссов из PRD без смягчений.

## 7. Безопасность: что защищаем

- Файл без пароля не читается: Argon2id 64 MiB, 3 итерации, AES-256-GCM.
- Подмена байтов, заголовка или обёртки ключа ловится тегом GCM.
- Откат ловится через `revision` и хеш заверенного файла.
- Нет сети — статус `Offline`, а не ложный `Verified`.

**На экране:** таблица «угроза → защита» из THREAT_MODEL, четыре строки.

## 8. Безопасность: что не защищаем

- Скомпрометированное устройство: root, вредонос, дамп памяти. Dart не гарантирует обнуления памяти.
- Откат между заверениями: если правки не заверены, подмена на последнюю заверенную версию даст «Verified».
- Upgrade authority программы у одного ключа разработчика. Для mainnet нужен мультисиг.

**На экране:** три строки «не защищаем» из THREAT_MODEL с колонкой «как смягчаем».

## 9. Что проверено и что нет

- Автотесты: `core/solana` проходят, интеграция с devnet — 3 из 3 (23.11.2026).
- Ручная проверка на Android-эмуляторе. Реального телефона и Windows вручную не было.
- Экспериментальная передача заметок (NFC/Nearby) вне MVP, см. ADR 0008.

**На экране:** две колонки «проверено» и «не проверено» — без украшений.

## 10. Roadmap

- Ручная проверка на реальном Android-телефоне и на Windows.
- Мультисиг или отказ от upgrade authority до mainnet.
- Напоминание о заверении, когда версия отстаёт (MAIN-43).
- Биометрия и вложения — только если останется время (Should have в PRD).

**На экране:** три колонки «сейчас», «после защиты», «вне MVP».
